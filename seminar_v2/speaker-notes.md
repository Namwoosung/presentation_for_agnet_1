# 발표자 노트

## F006 — Hermes 구조
왼쪽은 실행을 시작하는 입구이고 중앙은 요청을 이어가는 AIAgent입니다. 모델은 추론을 제공하며 Tool handler가 실제 작업을 수행합니다. 아래의 prompt와 session은 각각 모델 입력 구성과 상태 유지에 관여합니다. Gateway와 Cron을 모델 안의 기능으로 이해하면 안 됩니다. Cron은 새 실행을 시작합니다. 정책과 OS·DB 권한의 적용 범위는 구분해서 검토해야 합니다.

질문: Hermes Agent와 Hermes 모델은 같은 것인가요? 답: 실행 Harness와 모델 계열은 별개의 대상입니다.
질문: 모든 Tool은 승인을 거치나요? 답: 설정, Tool 종류, 실행 환경에 따라 확인해야 하며 그림은 일괄 승인 보장이 아닙니다.
연결: 이제 Runtime과 모델 사이를 한 번의 호출 단위로 살펴봅니다.

## F009 — 실행 시퀀스
모델에 전달하는 것은 실행 가능한 Tool의 설명입니다. 모델이 반환하는 Tool Call은 실행 요청이며 Runtime이 실제 handler를 호출합니다. handler 결과를 대화에 넣은 뒤 다음 모델 요청으로 진행합니다. 도식은 정상 경로만 보여주며 정책 거부, 취소, 오류 분기는 별도로 설명해야 합니다. BIN-X는 합성 사례이며 화면에 실제 관찰 이벤트는 없습니다.

질문: 모델이 DB 비밀번호로 직접 접속하나요? 답: 이 구조에서는 handler가 실행 자원과 권한으로 접속합니다.

## F049 — Deps 경계
RunContext.deps의 DB 객체와 principal은 애플리케이션 실행 환경의 자원입니다. 객체 자체를 자동으로 provider 메시지에 직렬화하지 않습니다. Tool이 이 자원을 사용하고 선택한 반환 데이터를 모델 입력에 넣을 수 있습니다. 화면의 select_allowed는 애플리케이션이 구현할 의사코드이며 SDK 제공 함수가 아닙니다. instructions에도 deps를 명시적으로 사용할 수 있으므로 자동 유출 방지를 보장하는 보안 경계로 오해하지 않아야 합니다.

질문: Deps에 넣으면 비밀정보가 항상 안전한가요? 답: 지침, Tool 결과, 로그에 직접 넣으면 노출될 수 있습니다.

## F066 — 위임과 제어권
왼쪽에서는 Specialist의 결과를 Manager가 받습니다. 최종 사용자 답변은 Manager가 조합합니다. 오른쪽에서는 handoff 후 Agent B가 활성 Agent가 되어 해당 turn의 나머지를 담당합니다. 입력 이력 필터링과 guardrail 범위는 별도의 설정과 검증 대상입니다.

질문: 둘 다 전문가를 호출하니 같은 것 아닌가요? 답: 결과가 원래 담당자에게 돌아오는지, 활성 답변 주체가 바뀌는지가 다릅니다.

## F091 — 배치 구조
두 배치는 같은 중앙 모델을 사용할 수 있습니다. 중앙 Runtime은 사용자 격리, 큐, 비밀정보 관리와 취소 처리 등을 운영해야 합니다. 로컬 Runtime은 OS 권한, 서명된 설치와 업데이트, 인증과 요청 한도를 관리해야 합니다. 모델 서버의 GPU 동시성 제한과 Agent 사용자 동시성은 별개입니다. 화면은 구현 완료를 주장하는 배포도가 아니라 설계 대안입니다.

질문: 중앙 모델이면 Agent도 중앙에 있어야 하나요? 답: 아닙니다. 로컬 실행 자원과 중앙 모델 API를 조합할 수 있습니다.
